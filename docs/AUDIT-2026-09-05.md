## Confirmed defects

### 1. One unauthenticated request kills the public relay (two lines, one missing guard)
[packages/relay/src/server.ts:302](packages/relay/src/server.ts:302) · also [packages/relay/src/server.ts:349](packages/relay/src/server.ts:349), [packages/relay/src/server.ts:452](packages/relay/src/server.ts:452)

The request handler's first statement is `const url = new URL(req.url || "/", "http://localhost")`, and the `/updates/` route then calls `decodeURIComponent(url.pathname.slice(...))`. Both throw on targets llhttp accepts verbatim, both are outside any try/catch, and there is no `uncaughtException` handler anywhere in the repo (`grep` over `packages/` and `apps/` returns nothing but a vendored Stream Deck bundle).

**Failure:** `GET //%25 HTTP/1.1` → `new URL` reads `%25` as an invalid host → `TypeError [ERR_INVALID_URL]` → process exit 1. `GET /updates/%C0%80` → `URIError: URI malformed` → same. Reproduced against the real `startRelay` from `packages/relay/dist`: `/health` answered 200, the next request exited the process with `at Server.<anonymous> … at parserOnIncoming`. Every publisher and viewer socket dies with it; a loop keeps `relay.supr.systems` down and can trip systemd's start limiter. Traefik forwards both targets unchanged, and README:210 notes 8787 is open directly anyway. The upgrade handler at :452 has the identical construct, so the WebSocket path crashes the same way pre-auth.

**Fix:** wrap the whole `http.createServer` callback and the `upgrade` handler in try/catch returning 400, parse with a `try { new URL(...) } catch { 400 }`, and move `decodeURIComponent` inside a try (or drop it — the sibling `/watch/` route at :415 does not decode). Add a `process.on("uncaughtException")` in `packages/relay/src/cli.ts` as the backstop.

### 2. Any writable `updateFeedUrl` is code execution as the user
[apps/standalone/src/updater.ts:97](apps/standalone/src/updater.ts:97)

`mod.setFeedURL({ provider: "generic", url: feedUrl })` takes the config value with no scheme check and no host allowlist, under `mod.autoDownload = true` ([updater.ts:81](apps/standalone/src/updater.ts:81)) and `mod.autoInstallOnAppQuit = true` ([updater.ts:83](apps/standalone/src/updater.ts:83)). `apps/standalone/package.json`'s `win` block has no `publisherName` and no signing, and the built `resources/app-update.yml` carries none either — so electron-updater's `NsisUpdater.verifySignature` returns early (`if (publisherName == null) return null`) and the only integrity check is the sha512 in the attacker's own `latest.yml`.

**Failure:** a sandboxed iframe on any web page (opaque origin → `Origin: null`) POSTs `{"updateFeedUrl":"https://evil.example/"}` to `http://127.0.0.1:47477/config` — accepted, see #3. `configStore.update` persists it, and on the next launch the app fetches `evil.example/latest.yml`, downloads the referenced `.exe`, verifies it against that same file's hash, and runs it on quit with the user's privileges. Chrome's private-network gating blocks the drive-by leg today; Firefox does not, and a plain `http://` feed is equally accepted, so a LAN attacker can MITM a legitimately configured self-hosted feed.

**Fix:** require `https:` and pin the host to an allowlist (the packaged GitHub feed plus whatever the user explicitly confirms in a dialog), and set `win.publisherName` + code signing so electron-updater's signature check actually runs.

### 3. Loopback control API: no auth, `Origin: null` allowed, viewer token still leaks
[packages/companion/src/controlServer.ts:25](packages/companion/src/controlServer.ts:25) · also [controlServer.ts:88](packages/companion/src/controlServer.ts:88), [controlServer.ts:107](packages/companion/src/controlServer.ts:107), [apps/standalone/src/main.ts:405](apps/standalone/src/main.ts:405)

`allowedOrigin` returns true for `origin === "null"` (comment: "file:// property inspector"), and :76 echoes it back as `Access-Control-Allow-Origin: null` — which matches a sandboxed iframe's opaque origin, so any web page can read the body. `guardPost` is `if (req.headers[CONTROL_CLIENT_HEADER]) return true` — header *presence*, no secret — and the OPTIONS preflight advertises that exact header name. `GET /status` and `GET /link` have no guard at all. Since b767273, `redact()` masks the four `SECRET_FIELDS`, so the API keys no longer leave; **`relay.viewerUrl` is a shallow-spread passthrough and still embeds the raw `viewerToken`** (`https://relay.supr.systems/watch/<token>`), and `GET /link` at :107 returns it without going through `redact()` at all.

**Failure:** a page you visit reads the viewer link and watches your live captions over the internet, then POSTs `/config` (`applyConfig` → `configStore.update` merges any key with no allowlist) to repoint `relayUrl`/`publisherToken` at its own relay, or to set `updateFeedUrl` per #2. `POST /start` and `/link/rotate` are reachable the same way.

**Fix:** the `"null"` allowance is the hole in a control the author deliberately built. Give the control API a real credential — a per-launch token the app writes to `%APPDATA%` and the property inspector reads — and gate reads as well as writes on it; keep the origin allowlist as defence in depth rather than the only gate.

### 4. Installer downloads: an I/O error kills the relay, and every aborted download leaks a descriptor
[packages/relay/src/server.ts:409](packages/relay/src/server.ts:409) · also [packages/relay/src/server.ts:399](packages/relay/src/server.ts:399)

`fs.createReadStream(file).pipe(res)` (and the `{ start, end }` Range twin) registers no `error` listener on the source. `Readable.pipe` attaches `onerror` to the *destination* only, so a source error is emitted with zero listeners → uncaught → process exit. `pipe` also never destroys the source when the destination closes.

**Failure (crash):** EMFILE, or an EIO mid-read, on the unauthenticated `/updates/<installer>.exe` route takes the whole relay down mid-broadcast. **Failure (leak):** measured — 25 aborted downloads left 25 `ReadStream`s with `destroyed=false, closed=false`, all holding fds, and a forced-GC run showed fds are never reclaimed (`fs.ReadStream` holds a raw fd, no finalizer). Enough aborts and the process hits `RLIMIT_NOFILE`, after which new sockets and `statSync` fail and the relay stops serving without crashing or logging a cause — which then triggers the crash above.

**Fix:** replace both `.pipe(res)` calls with `stream.pipeline(rs, res, err => …)`, or at minimum `rs.on("error", …)` plus `res.on("close", () => rs.destroy())`.

### 6. A failed relay restart leaves the app permanently dead — and reports success
[apps/standalone/src/main.ts:405](apps/standalone/src/main.ts:405) · also [main.ts:166](apps/standalone/src/main.ts:166), [main.ts:161](apps/standalone/src/main.ts:161), [renderer/app.ts:1147](apps/standalone/renderer/app.ts:1147), [renderer/app.ts:1159](apps/standalone/renderer/app.ts:1159), [renderer/app.ts:578](apps/standalone/renderer/app.ts:578), [packages/relay/src/server.ts:706](packages/relay/src/server.ts:706)

### 8. Offline local STT has no backpressure and can never catch up
[packages/relay/src/localSttWorker.ts:288](packages/relay/src/localSttWorker.ts:288) · also [localSttWorker.ts:285](packages/relay/src/localSttWorker.ts:285), [packages/relay/src/localStt.ts:226](packages/relay/src/localStt.ts:226)

Each partial re-decodes the whole open VAD segment, gated on `st.sincePartial >= PARTIAL_EVERY_SEC * SAMPLE_RATE` — *buffered audio samples*, not wall clock. With `maxSpeechDuration: 15` that is ~12 partials plus a final per segment, per channel, on one worker thread. The producer never measures depth: `send({ type: "audio", buffer: ab }, [ab])` posts a 100 ms chunk and returns, and Node's port queue is unbounded. The only drop path (`droppedBytes += chunk.length`) sits inside `if (!ready)` and is dead once the worker has answered `ready`.

**Failure:** pick `local-whisper-turbo` (catalogue `speed: 1`, "each phrase takes seconds on a CPU") with two sources. Decode runs slower than realtime, the queue grows monotonically at up to 64 KB/s, and because the partial gate counts buffered samples the backlog is replayed at full cost — captions fall further behind wall clock every minute with no drop, no warning and no recovery for the session.

**Fix:** gate partials on wall-clock time and skip a partial when the queue is behind; track queue depth in `localStt.ts` and drop (and report, as the pre-`ready` path already does) once it exceeds a bounded number of seconds.

### 9. Viewer reconnect opens a second socket; the relay's kick then closes the live one
[packages/viewer/public/app.js:333](packages/viewer/public/app.js:333) · also [app.js:392](packages/viewer/public/app.js:392), [app.js:405](packages/viewer/public/app.js:405)

`connect()` has no re-entrancy guard and does not cancel the armed `setTimeout(connect, 2000)`, and every handler acts on the module-level `ws` rather than the socket that raised the event. The `visibilitychange` handler also clears `closedByKick` unconditionally.

**Failure:** a phone viewer's socket drops; `onclose` arms a 2 s retry. The user unlocks the phone inside that window, `visibilitychange` calls `connect()` (socket A), then the timer fires and `connect()` runs again (socket B, `ws = B`). The relay allows one viewer per token, so `onViewer` kicks A; A's still-bound `onmessage` sets `closedByKick = true`, shows the ENDED screen and calls `ws.close()` — on **B**, the healthy socket. A live session displays "THIS LINK HAS ENDED" and stops receiving captions, with no reconnect, until a full page reload. Separately, on a genuinely rotated token the same `closedByKick = false` reset restarts a flat 2 s reconnect loop against a dead token forever.

**Fix:** in `connect()`, `clearTimeout` the armed retry and close any existing socket first; capture the socket in a local and have every handler check `if (sock !== ws) return;` before acting (this is exactly the fix cc824dd applied to `relayClient`/`uplinkClient`); only clear `closedByKick` when the user explicitly retries.

### 11. STT death is never surfaced and the relay keeps reporting the stream live
[packages/relay/src/deepgram.ts:90](packages/relay/src/deepgram.ts:90) · also [session.ts:212](packages/relay/src/session.ts:212), [server.ts:260](packages/relay/src/server.ts:260), [server.ts:231](packages/relay/src/server.ts:231), [server.ts:706](packages/relay/src/server.ts:706), [session.ts:265](packages/relay/src/session.ts:265)

`ws.on("close", () => { if (!closedByUs) events.onClose?.(); })` — no reconnect anywhere in `packages/relay` (only `gemini.ts` has a retry ladder), and the close code/reason are discarded. `session.onClose` logs and broadcasts `status live:false` but, unlike `onError`, never calls `deps.onSttError`, which is the only channel that reaches the publisher app. `deps.setLive` is `() => {}` at the server, and `isLive()` is pure socket presence, so `/health` and every viewer `hello` keep saying live. ### 14. An env API key is re-injected on clear and written into `config.json`

### 15. A stop landing during `start()` is silently undone; devices stay captured while the UI says idle
[packages/companion/src/capture/index.ts:162](packages/companion/src/capture/index.ts:162)

`start()` awaits device acquisition (`getDisplayMedia`/`getUserMedia`) and worklet module load, then unconditionally installs its state and sets `this.active = true`. There is no generation counter and no post-await cancellation check, and `stop()` only clears state `start()` has already written.

**Failure:** press START, then STOP (or open KEYS — the button reads STOP during "starting" and four call sites deliberately allow it) while the loopback source is still opening. `stopSession` runs `capture.stop()`, which finds `active === false` and releases nothing, and sets the UI to idle. `start()` then resumes and installs a live AudioContext with the mic and loopback streams. ### 16. Gemini truncation at `maxOutputTokens: 120` is accepted as a complete translation and cached
[packages/relay/src/gemini.ts:116](packages/relay/src/gemini.ts:116) · also [gemini.ts:133](packages/relay/src/gemini.ts:133), [gemini.ts:166](packages/relay/src/gemini.ts:166)

`attempt()` never reads `candidates[0].finishReason` — `grep` for it across `packages/`, `apps/` and `scripts/` returns nothing. The only rejection test is `if (!out)`.

### 17. The 4 s kill timer discards the worker's flush finals
[packages/relay/src/localStt.ts:149](packages/relay/src/localStt.ts:149) · also [localStt.ts:147](packages/relay/src/localStt.ts:147)

`close()` posts `{type:"close"}` at the *back* of the worker's audio queue and then hard-terminates the thread 4 s later. The worker must drain every queued chunk and run `flush()` — `vad.flush()` plus `decodeOffline(seg.samples)` for each channel — before it can emit the closing finals.

**Failure:** on a heavy offline model with two channels, the last utterance before STOP never reaches viewers: `finish()` sets `done = true` and terminates at t+4000, and the `if (done) return` guard drops any final that arrives after. Worse, if STOP lands while audio is still queued from the model-load window (the buffer deliberately holds up to `PROBE_TIMEOUT_MS` of speech), the whole backlog gets 4 s and is then thrown away with no error surfaced.

**Fix:** send the close out-of-band (a separate control port or an `AbortSignal` the worker polls) so it is not queued behind audio, and scale the kill deadline to the queued backlog rather than using a flat 4000 ms.

### 19. Re-entered setup rejects a working key and locks step 1
[apps/standalone/renderer/app.ts:1242](apps/standalone/renderer/app.ts:1242) · also [app.ts:1244](apps/standalone/renderer/app.ts:1244)

RUN SETUP AGAIN (which sits in the same pane) puts the good key back into the field but keeps the stale verdict, so step 1 prints "KEY REJECTED" and disables CONTINUE for a key that works; the stage's 02 TRANSCRIBE meta reads "KEY INVALID" too. **Fix:** key the cache by the value that was validated (`keyCheck[provider] = { key, result }`) and treat a verdict for a different string as absent.

### 20. The tray and Stream Deck hand out the `?obs=1` overlay URL as the phone link

### 22. Translation failures are logged once and never reach the user
[packages/relay/src/session.ts:199](packages/relay/src/session.ts:199)

### 23. The 48 kHz → 16 kHz downsample has no anti-alias filter
[packages/companion/src/capture/index.ts:112](packages/companion/src/capture/index.ts:112) · also [workletSource.ts:16](packages/companion/src/capture/workletSource.ts:16), [workletSource.ts:52](packages/companion/src/capture/workletSource.ts:52)

`new AudioContext()` takes no options, so the graph runs at the device rate, and the worklet drops to 16 kHz by linear interpolation with a one-sample history. At the common 48 kHz the step is exactly 3 and the interpolation weight is identically 0 — pure decimation, no filtering.

**Failure (measured by running the shipped worklet source):** at 48 kHz a 12 kHz tone comes out as a 4 kHz tone at **0 dB attenuation**; 15 kHz → 1 kHz, 20 kHz → 4 kHz, all full amplitude. Everything from 8-24 kHz folds into the 0-8 kHz band the acoustic model reads — game transients land on the formant region and sibilance smears onto its own aliases, on every session.

**Fix:** one line — `new AudioContext({ sampleRate: TARGET_SAMPLE_RATE })`. Chromium then resamples the source with its own windowed-sinc filter, the worklet's step becomes 1 and the loop degenerates to passthrough (already covered by the existing `[16000, "no resampling at all"]` test case).

### 24. The uplink fights a 4409 kick forever, and the 4401 branch is dead code
[packages/companion/src/uplinkClient.ts:119](packages/companion/src/uplinkClient.ts:119) · also [server.ts:467](packages/relay/src/server.ts:467)

The relay closes a displaced uplink with 4409; `RelayPublisherClient` handles that code and stops, but `UplinkClient` special-cases only 4401 and falls through to `scheduleRetry`. Combined with the attempt reset on open, that is a fixed 1000 ms. The 4401 branch it does have is unreachable: a bad token is refused during the HTTP upgrade (`socket.write("HTTP/1.1 401 …")`), which surfaces as close code 1006.

**Failure:** two machines sharing one `publisherToken` displace each other roughly once a second forever, and `bridgeBroadcasts` drops every subtitle produced in each gap. Separately, a wrong or stale remote token retries forever and the UI shows "RELAY CONNECTING…" indefinitely — the "RELAY ERROR · CHECK KEYS" state that exists for exactly this case can never fire.

**Fix:** handle 4409 the way `relayClient.ts:139` does (set error, do not retry), and either send a real 4401 close (accept the upgrade, then close) or detect the 401 handshake failure in `onerror` and latch an error state.

### 25. Two concurrent model downloads collide on the shared VAD `.part`
[apps/standalone/src/models.ts:62](apps/standalone/src/models.ts:62) · also [models.ts:72](apps/standalone/src/models.ts:72), [models.ts:111](apps/standalone/src/models.ts:111)

### 26. An archive failure always blames the transport, never the archive
[apps/standalone/src/models.ts:201](apps/standalone/src/models.ts:201)

`if (declared > 0 && received < declared)` compares bytes read off the response body against `content-length`, but the body is only pulled as fast as the bz2/tar pipeline consumes it. Any mid-stream decode failure destroys the body with most of it unread, so the check reports a truncated download — the opposite of what it was added to determine.

**Failure (reproduced with the repo's own `unbzip2-stream` and a real multi-block archive):** one flipped bit 30 % in, transport perfect → `the download stopped early: 2752512 of 6324614 bytes (43%) - Error in bzip2: crc32 do not match`. A genuinely truncated stream → the same verdict. The corrupt-archive branch is unreachable outside the final read-ahead window. This lands directly on the open ~28 % bzip2 bug and will point triage at the network even when every byte arrived.

**Fix:** decide from the transport, not the counter — resolve the body's `end` event (or `res.body` completion) separately from the pipeline, and report "archive would not unpack" whenever the source finished.

## Assessment

The relay is the fragile part, and it is the part exposed to the internet: its HTTP and WebSocket handlers parse untrusted input with no try/catch, pipe files with no source error handler, and run in a process with no `uncaughtException` handler anywhere — so several one-line requests are equivalent to a kill switch on `relay.supr.systems`, and the recent "do not let a malformed hello take the relay down" fix patched one instance of a pattern that recurs four more times. On the desktop side the recurring shape is *persist-then-validate with no rollback and a success message either way*: `applyConfig` writes to disk before it knows the change works, `restartEmbeddedRelay` tears down the working relay first, the renderer swallows the rejection and logs "keys & relay saved", and state that only ever promotes (`recomputeState`, `capturing`, `isLive`) leaves the UI asserting LIVE over a dead pipeline. Third, the loopback control API's "no auth by design" assumption is quietly false — a CORS policy that admits `Origin: null` hands the whole surface, reads and writes, to any web page the user visits, which is what turns the unpinned update feed from a configuration choice into remote code execution.
